# How to add an algorithm

Adding an algorithm is how this project grows (`PROPOSAL.md` §15). This page walks the whole path
on a real, small step: **`Normalise`**, which divides each spectrum by its l1, l2, max or area norm.
Every file and test named below exists. Read each one next to this page, and a new step is the
same shape.

The order matters: specification, reference, kernel, parity, schema, executor, screen. Each layer
is checked before the next one is written.

## 1. The specification

Write down what the step computes before you write any code. Name the variant, the conventions,
and every quantity the step reports, and say where the definition differs from other tools.
"Normalise" is not a specification. "Each row divided by its l1, l2 or max norm, or by its signed
sum for `area`" is.

New algorithms get a section in [`docs/algorithms/`](algorithms/pca.md). `Normalise` predates that
rule, and its one divergence is recorded in the module docstring of
`src/chemometrics_workbench/preprocessing.py`, under *Known divergences*: `area` divides by the
signed sum of the row, while some tools integrate by the trapezoid rule instead.

A step that estimates something from the other samples, as MSC and mean centring do, has to say so
too. That decides whether it may sit above a cross-validation split
([metrics and validation §9](algorithms/metrics-and-validation.md)). `Normalise` works row by row,
so it may.

## 2. Reference values

A kernel with nothing to check it against cannot be trusted. Reference values come from published
literature or an established open implementation, with its version recorded. Add them as entries
in `tests/fixtures/reference_values.json`, generated by `tests/fixtures/generate_reference_values.py`.

`Normalise` is checked against `sklearn.preprocessing.normalize`. The generator writes one entry per
dataset and norm, `<dataset>.preprocess.normalised_<norm>.sklearn`, with the preprocessing chain,
the variant, the software version and a note. Regenerate with:

```bash
uv run python tests/fixtures/generate_reference_values.py
```

`area` has no scikit-learn counterpart, so it has no reference entry. Its behaviour is pinned by
unit tests instead. A value that cannot be sourced goes into the fixture as `status: "unsourced"`
with the reason. It is never left out, and never filled in with a plausible number.

scikit-learn is a **development** dependency. The kernel never imports it: a kernel built on the
reference would be checking the reference against itself.

## 3. The kernel

The kernel is a pure function over arrays, shaped `n_samples × n_variables`. It must not mutate the
caller's array, must not use global random state, and must know nothing about the application.
`NormaliseTransformer` in `preprocessing.py` follows the `fit` / `transform` shape every
transformer there has. Its failure modes are errors that name the row. A spectrum summing to zero
cannot be area-normalised, and `test_a_row_summing_to_zero_stops_area_normalisation` holds that.

## 4. The parity claim

Parity is tested through the shared harness, never with a bare `assert_allclose`.
`tests/test_parity.py`:

```python
@every_dataset
@pytest.mark.parametrize("norm", ["l1", "l2", "max"])
def test_normalisation_matches_the_reference(dataset: str, norm: str) -> None:
    ours = NormaliseTransformer(norm).fit_transform(_block(dataset))
    assert parity.check(f"{dataset}.preprocess.normalised_{norm}.sklearn", ours).passed
```

`@every_dataset` makes one test of the claim on corn, gasoline and Tecator: every dataset's
comparison runs and is recorded even when an earlier one fails, and a failure names each dataset
that failed. `parity.check` picks the tolerance for the quantity's class. `tests/parity.py` maps `normalised_l2`
to `preprocessing`. It then tags the claim's tier and records the result for the
[parity report](parity-report.md). **Tolerances are not knobs.** A comparison that fails is a
finding, not a number to widen.

```bash
uv run pytest -m parity
uv run python -m tests.parity_report     # regenerates docs/parity-report.md; commit it
```

## 5. The pipeline model

A step exists for the application only once the schema knows it. In
`src/chemometrics_workbench/models.py` it is a frozen Pydantic model with a literal `kind`:

```python
class Normalise(Frozen):
    kind: Literal["normalise"] = "normalise"
    norm: Literal["l1", "l2", "max", "area"] = "l2"
```

It is also a member of the `PreprocessStep` discriminated union, so an invalid configuration fails
when it is parsed rather than halfway through a run. Bounds and descriptions go on the fields
(`Field(ge=..., description=...)`). The inspector shows them.

If the step estimates something across samples, add it to `_FITTED_ACROSS_SAMPLES` in `checks.py`.
`Normalise` does not, and `test_a_step_that_estimates_nothing_may_sit_above_a_split` asserts that.

## 6. The executor

`preprocessing.from_spec` turns a `PreprocessStep` into its transformer, and it is the executor's
only entry point:

```python
case Normalise():
    return NormaliseTransformer(step.norm)
```

The executor itself is generic. It calls `from_spec`, fits on the fold's training rows and
transforms, so a new preprocessing step needs nothing else there.
`test_every_supported_step_round_trips_through_the_schema` in `tests/test_preprocessing.py` builds
every step from its JSON. Add the new one to its cases.

If the model can be exported, `export.py` says how. `Normalise` is carried as a residual step
([model export](model-export.md) §1). A step that cannot be exported is refused by name, never
approximated.

## 7. The screen

The inspector needs no code. It builds each node's form from `GET /api/schema/steps`, which is
`models.py`'s JSON schema, so the field bounds shown are the model's own bounds.

What does need code is how the step is offered and named:

- `frontend/src/canvas/catalogue.ts` adds an entry to the **Step** list:
  `{ kind: "Normalise", type: "preprocess", parameters: "l2 norm per row", payload: { step: { kind: "normalise", norm: "l2" } } }`;
- `nodeLabel` in `frontend/src/shell/Sidebar.tsx` gives the outline name, `Normalise · l2`;
- `parameterLine` in `frontend/src/canvas/graph.ts` gives the canvas line, `l2 norm per row`.

`frontend/src/__tests__/catalogue.test.ts` and `graph.test.ts` pin all three. `Normalise` was
accepted by the server long before the step list offered it. This walkthrough added that last
layer (#238).

## 8. Checks before the pull request

```bash
uv run ruff check && uv run ruff format --check && uv run mypy && uv run pytest
cd frontend && pnpm typecheck && pnpm lint && pnpm test && pnpm build && pnpm test:e2e
```

Then open the pull request into `dev`, as [CONTRIBUTING.md](https://github.com/millermuttu/Chemometrics-Workbench/blob/dev/CONTRIBUTING.md)
describes. A change that moves a reported number updates the fixtures and the parity report in
the same commit, and says why in the message.
